# Design Shape Register

> **Before you match any candidate to a shape — classify, then measure.** A symptom ("a low-privilege caller obtained data or power they lack directly") maps to several different structures, half of them Working-As-Intended. (1) **Classify the structure** with four questions — Q1 what the caller controls (resource reference / identity binding / operation on an already-bound identity), Q2 deputy type (provider-managed service agent vs customer-managed service account), Q3 bind vs use, Q4 exceed-vs-stay-inside the identity's scope — and route to the shape the *structure* matches, not the one you went hunting for. (2) **Measure the delta, not the mechanism**: a candidate is confirmed only if the Measurement Triad holds — **baseline** (the caller could not already get it), **ceiling** (the result exceeds the bound identity's own scope), **attribution** (the borrowed authority, not the caller, performed it), and an **observation channel** (the data actually reached the attacker).

## Reusable Vulnerability Shapes

> **Purpose**: This register sits between the Design Flaw Canon and the Security Constitution prompt. The canon stores concrete cases, the feature-abuse catalog stores counterexamples, the Discovery Signal Register stores documentation/API clues, and this register stores the reusable **vulnerability shape** a reviewer should validate and distinguish from legitimate powerful features.

> **Cardinality:** Each DFC is one reported insecure-by-design instance and may map to one or more Shapes. Shapes are reusable generalizations, not DFC containers. Shape-to-Signal mapping is many-to-many: a Shape may link to multiple Signals, and a Signal may route to multiple Shapes.

---

## How This File Relates to the Others

- `feature-abuse-reference.md` stores negative calibration cases the model should reject as non-flaws.
- `discovery-signal-register.md` stores documentation/API clues that route investigation toward shapes, hypotheses, and probes.
- `design-shape-register.md` generalizes cases and counterexamples into reusable, testable vulnerability shapes.

Discovery signals and vulnerability shapes are deliberately separate: a signal says "look here"; a shape says "this is the missing-control structure to validate." Neither relationship is one-to-one. A DFC may contribute multiple Shapes; a Shape may expose multiple Signals; and a Signal may route to multiple Shapes. The shape register is a **Phase 1 artifact**; Phase 2 turns it into Security Constitution prompt guidance.

## Shapes

> This public edition ships the five shapes behind the cases presented at the talk (`SHAPE-001`, `013`, `016`, `021`, `032`). The IDs follow the full research taxonomy, so the numbering is intentionally non-contiguous. Entries are abstract by design — they describe the *structure* of a flaw and the control whose absence creates it, so you can point your own harness at your own attack surface — not any specific provider finding.


### SHAPE-001: Provider-Managed Service-Agent Effective-Permission Invocation Without Caller Authorization

| Field | Detail |
| ---------------------------------- | ------ |
| **Core question** | Can a caller-controlled product-API request cause a provider-managed service agent to exercise its effective permissions on caller-supplied resources, code, data, images, outputs, secrets, connections, or networks without first verifying that the caller independently holds the corresponding direct permission? |
| **Trust boundary** | Invoking caller → provider-managed product API → provider-managed service agent → caller-supplied secondary resource or execution dependency |
| **Missing control** | A caller-bound authorization check on the referenced resource or dependency before the service agent exercises its effective permission. (On GCP this is caller-bound IAM on the referent; on AWS the caller-bound forwarding / `aws:ViaAWSService` model usually keeps authorization tied to the caller, which is why this shape does not port directly to a documented AWS service-role workflow.) |
| **Discovery signal links** | Primary: `SIGNAL-001` (a provider-managed service agent acts on a caller-referenced resource). A defaulted/managed runtime-authority signal is a secondary route. |
| **Safe-control / negative signal** | The service backend performs a caller-bound authorization check on the invoking principal against the caller-supplied resource before the agent acts. Also safe when the deputy is a **customer-managed** service account the caller binds (→ `SHAPE-016`) or merely uses (the invoker model → `FA-013`), since the attachment gate (`iam.serviceAccounts.actAs`) is structurally inapplicable to a provider-managed agent. **Demote** even a genuine missing-check when the reached primitive is **type-locked** — the service permission's documented purpose already grants exactly the reachable data (a one-for-one stand-in), with no broader content type reachable and no arbitrary-byte write. Score read and write separately; demote only when both are type-locked. A managed service that reads a caller-named input **as the caller** (caller must already hold the read permission) is the safe pattern; the unsafe outlier is one that reads via the **service agent**. |
| **Canon anchors** | None in this edition (the canon names specific cases and is not shipped here). |
| **Feature-abuse anchors** | `FA-006` (service-account impersonation); `FA-010` (rule-based compute-to-identity inheritance with customer-authored gates). |
| **Severity sizing** | By what the reached resource unlocks × boundary, and only once the Measurement Triad holds. A type-locked primitive returning exactly the caller's documented data is not an escalation. |
| **Security Constitution lesson** | For service-agent paths, do not ask only whether the service agent is authorized. Ask whether the invoking caller was authorized for the resource the agent used. Record permission provenance (`automatic`, `documented-admin-grant`, `customer-configured`, `bootstrap-only`) separately from exploitability. Treat cross-project references, async/sync run jobs, docs instructing grants to service agents, and automatic data-plane roles as strengthening signals rather than standalone proof. |
| **Decoys** | "The service agent acted / the request was accepted" is the **mechanism**, not a finding. Require that the data reaches the caller (observation channel) and exceeds what the caller's own role already grants. |
| **Confused-with** | `SHAPE-016` if the deputy is a customer-managed SA the caller **binds** (control = the attachment gate, not caller-authz). The invoker model (`FA-013`) if the caller **uses** an already-bound customer-managed SA (WAI). `SHAPE-013` if the referent is a network attachment. Discriminator: provider-managed agent → this shape; customer-managed SA → one of the others. |

### SHAPE-013: Caller-Supplied Network-Attachment Deputy (Managed Connector Cross-Tenant Network-Presence Pivot)

| Field | Detail |
| ---------------------------------- | ------ |
| **Core question** | Can a caller-controlled product-API field that references a **network or connectivity resource** (PSC network attachment, VPC connector, private endpoint, hybrid connection, peering reference) cause a managed service's shared deputy/connector fleet to **establish network presence inside, or originate traffic toward, a network the caller is not authorized to use** — with no caller-bound check on that network resource — when cross-boundary admission is gated only by an owner-side accept-list the deputy does not bind to the specific caller, and the deputy identity is shared across tenants? |
| **Trust boundary** | Invoking caller (tenant B, no rights in tenant A) → managed service control plane → shared provider-managed connector/producer fleet → caller-named network attachment inside tenant A's VPC → internal-only resources reachable from inside that VPC |
| **Missing control** | (a) A caller-bound authorization check on the referenced network resource (e.g. `compute.networkAttachments.use`, or that the attachment belongs to the caller's project) enforced before the deputy establishes network presence, at both config-create and run; and (b) a per-tenant producer identity, so an owner-side accept-list can distinguish the owner's own use from any other tenant of the shared service. An owner-side accept-list alone is not a caller-authorization control. |
| **Discovery signal links** | Primary: `SIGNAL-010` (IAM is the sole gate on caller-supplied network reachability). Secondary routes: a cross-service reference handoff (a network attachment owned by one service dereferenced by another service's deputy), a shared-fleet severity multiplier, and a provider-created side-effect identity with no tenant inventory surface. |
| **Safe-control / negative signal** | Safe when the service verifies the caller's `.use`/ownership on the referenced attachment before the deputy acts; or the deputy connects through a customer-managed connector identity gated by the attachment gate (`FA-006` territory); or the producer is **per-tenant** so owner-side allowlisting scopes admission to the owner's own use; or the deputy can only reach networks the caller already controls. **Two axes both required** for a real finding: (1) a **shared** deputy fleet (per-project service agents are cross-tenant-safe because granting a *foreign* tenant's service agent access is not a routine operation), and (2) the caller's authoring permission does not already semantically include the network capability. A managed orchestration wrapper whose service identity is designed to stand in for resource IAM is WAI for resources it exists to operate (e.g. reading an attached disk); it is a candidate finding only where the missing `.use` gates a separately governed **network-reachability boundary** the wrapper is not chartered to cross, or where the reference overruns the project/tenant boundary. |
| **Canon anchors** | None. |
| **Feature-abuse anchors** | `FA-006` (customer-managed connector identity with the attachment gate enforced) is the adjacent calibration negative. |
| **Severity sizing** | A shared producer fleet can turn the missing caller-bind into an unconditional cross-tenant exposure (highest tier); a per-tenant/per-project deputy bounds it to within-project at most. |
| **Security Constitution lesson** | A managed service's privileged action can be **establishing network presence inside a customer's VPC**, so a caller-supplied network attachment is a protected reachability capability — and the `.use` permission is a network-team boundary control, not merely an implementation detail of an orchestration wrapper. Apply two separate axes (cross-tenant via a shared fleet; within-project via a resource-specific `.use` gap). Requiring the caller to duplicate ordinary wrapper permissions is WAI for resources the wrapper exists to operate, but not for a separately governed network-reachability boundary. |
| **Decoys** | A synchronous create-200 or a long-running-operation `done:false` is not a gate result. A per-project deputy blocks the cross-tenant variant but does not by itself reject a same-project resource-specific `.use` bypass. A wrapper using an ordinary input resource it is chartered to operate is WAI absent scope overrun; prove the missing `.use` protects a distinct reachability boundary and close the observation/effect loop. |
| **Confused-with** | `SHAPE-001` when the referent is a data resource rather than a network attachment; `SHAPE-019` for a free-form egress target from an existing network position; `FA-006` for a customer-managed connector identity with the attachment gate enforced. |

### SHAPE-016: Customer-Managed Run-As Binding or Activation Without the Attachment Gate

| Field | Detail |
| ---------------------------------- | ------ |
| **Core question** | Can a caller invoke a method that **binds or activates** a **customer-managed** service account in a run-as / identity field (a create/update, restore/clone, validation, build, or other one-shot operation) — making the resource or operation run with that SA's permissions — **without** the method verifying that the caller holds the attachment gate (`iam.serviceAccounts.actAs`, or the AWS `iam:PassRole` analogue) on the named SA? |
| **Trust boundary** | Invoking caller (holds the product binding/activation permission; **no** attachment gate on the named SA) → product-API identity-binding or one-shot activation method → the named customer-managed service account and all its IAM permissions → every downstream resource the operation can reach |
| **Missing control** | A caller-bound attachment-gate check (`iam.serviceAccounts.actAs` / `iam:PassRole`) on the named service account, enforced at the **binding/activation moment**, before the resource runs as that SA. The gate governs **binding/activation**, not later **use** of an already-bound resource. |
| **Discovery signal links** | Primary: `SIGNAL-015` (a caller-supplied customer-managed run-as service account on a binding/activation method). Secondary routes: a defaulted run-as identity, and the AWS customer-managed role-attachment gate analogue (`iam:PassRole`), which requires downstream-effect proof. |
| **Safe-control / negative signal** | Safe when the attachment gate is **enforced** (a caller without it is denied); when the run-as field is immutable / output-only / not in the update mask; when the method supplies only operational input (args, env, timeout) that cannot change the execution identity; when the run-as identity is a provider-managed service agent (the gate is then structurally inapplicable → route to `SHAPE-001`); or when the caller already holds the gate (no delta). Enforcement is a **live test, not an assumption**: documented-required-yet-not-enforced, with a sibling op that enforces it, is a reportable bug at any ceiling. The ceiling (what the borrowed identity then does — run attacker code vs a fixed internal action) sets **severity**, separately from whether the gap is confirmed. A caller-bound check on a resource the SA later *reads* is **not** this shape's control (that belongs to `SHAPE-001`); the SA's own IAM bounds its reach. |
| **Canon anchors** | None. |
| **Feature-abuse anchors** | `FA-006` (the safe version — a customer-managed run-as SA **with** the attachment gate enforced); `FA-013` (the binding-vs-use negative — the gate is not required to *use* an already-bound SA). |
| **Severity sizing** | By the bound SA's own IAM reach. A compute/job runner that executes attacker-controlled work as the SA yields the SA's full permission set (high); a fixed-purpose action yields no credentials/code-exec (low, but still reportable as an enforcement gap). |
| **Security Constitution lesson** | The attachment gate governs the **binding or activation** of a customer-managed identity, not the **use** of an already-bound resource. A restore, validation, build, or execute method can still be the binding moment when its request selects the SA; acceptance is only a signal until the selected SA is shown to perform the effect. Route provider-managed agents to `SHAPE-001`; do not propose a per-referenced-resource caller check on a customer-managed-SA path (that mistakes the `SHAPE-001` control for this one). |
| **Decoys** | "The request was accepted" is the mechanism; require the bound SA (not the caller) to perform a privileged action, or at minimum to persist as the run-as identity. Using an already-bound SA, or changing which resource it reads, is WAI. A caller who already holds the gate gains nothing. |
| **Confused-with** | `SHAPE-001` if the run-as identity is a provider-managed service agent (gate inapplicable → caller-authz is the control). The invoker model (`FA-013`) if the caller **uses** rather than **binds** the SA. Token-mint sibling: if the method mints the SA's **token** (attaches it to an outbound request) rather than making the resource run as the SA, the governing permission is the token-issuance permission (`getAccessToken`/`getOpenIdToken`), not the attachment gate — size impact by whether the token is replayable. |

### SHAPE-021: Secret Serialization / View-Mask Redaction Bypass (Read-Side Secret-Field Authz Gap)

> The **read-side dual of `SHAPE-020`**, sharing the same parent lesson ("operation-authority ≠ resource-authority") on the READ path: a permission that authorizes *reading an object* does not authorize reading every field's secret value. A `get`/`list`/`export` method exposes an inline secret through either **variant A**, a view/mask/format parameter that bypasses default redaction, or **variant B**, an always-on serialization of a value the platform otherwise treats as protected (write-only, masked, `NoEcho`, or dedicated-secret-gated). The coarse read permission is the only gate. Distinct from `SHAPE-001`/`013`/`019`: there is **no deputy** — the platform returns the secret straight to the caller — and no write (contrast `SHAPE-020`).

| Field | Detail |
|-------|--------|
| **Core question** | Does a READ method (`get`/`list`/`export`) return an **inline secret-bearing value** under only its coarse read permission, with no dedicated secret-access gate? Variant A: a default view redacts the field but a `FULL`/unmask/format path returns it. Variant B: no alternate view exists, but a protected-value signal (write-only sibling, masked behavior, a dedicated secret getter) shows the plain serialization is not intended for generic readers. |
| **Trust boundary** | Caller with a resource-READ role that lacks any credential/secret-access permission → the read method or projection → an inline secret field whose disclosure authority is narrower than the coarse read authority. No service agent or borrowed identity — the platform serializes the caller's own read into plaintext. |
| **Missing control** | **Read-authorization and response-serialization parity**: an unredacted view must require a dedicated secret permission, or protected values must never be serialized on a generic read path (return a reference or redacted value instead). Where IAM has no field-level sub-action, the service-side response contract is the control. |
| **Discovery signal links** | Read-side cues (inline, not a numbered signal): variant A — a default/`BASIC` view redacts the field while `FULL`/unmask returns it under the **same** read action; variant B — a read schema carries an inline credential while a write-only path, protected sibling, dedicated secret getter, or masked representation shows the value is sensitive. Sweep view enums and unmask parameters, then trace secret-bearing fields across every `get`/`list`/`export` projection. |
| **Safe-control / negative signal** | A dedicated secret permission is enforced; the value is never serialized; only a secret-store reference is returned; ciphertext is not recoverable by the tested principal; or the field is intentional visible configuration with no independent protection signal. A named privileged password-getter can be WAI when its own action is deliberately privileged. A list that redacts while a getter is privileged is also safe. |
| **Canon anchors** | None. The read-side dual of `SHAPE-020` (write-side). |
| **Feature-abuse anchors** | A `FULL` view that re-checks a dedicated secret-access permission; a field whose default and alternate views both return ordinary configuration; a leaked secret-store **reference** (recon only); a deliberately privileged password-getter. |
| **Severity sizing** | By what the disclosed secret unlocks × boundary. Third-party OAuth tokens / passwords / private keys → takeover of the connected external service; a provider IAM credential / cross-tenant token → higher; a secret-store **reference** only → recon. Blast radius scales with which read role carries the coarse permission — a basic project-viewer role widens it dramatically versus a specialized service-viewer role. |
| **Security Constitution lesson** | A permission that authorizes reading an object does not authorize reading every field's secret value. Default redaction is strong evidence of protection intent; always-on serialization requires an independent protection-intent signal, especially where IAM has no field-level sub-action and redaction lives in the service response body. This is not a confused deputy — the platform hands the secret to the caller directly — and it remains the read-side dual of `SHAPE-020`. Bind the finding to the **exact** operation × response shape: sibling read ops often use different projections (a summary shape may omit the secret a detail shape returns), and the same secret can appear at multiple sites within one response, so name the precise disclosing operation in both the finding and its remediation. |
| **Decoys** | A field being present in a schema is not proof. A field returned in every view with no protection-intent signal, a secret-store reference, unrecoverable ciphertext, an explicitly privileged getter, or customer-visible plaintext configuration is not automatically this shape. |
| **Confused-with** | `SHAPE-020` if the bypass is a **write** (mutating/disabling a security field via a coarse update permission) — this is its read-side dual. `SHAPE-001`/`013`/`019` if a managed **deputy** dereferences a caller-supplied referent (here no deputy). `IMPACT-001` is the *consequence* when the disclosed secret is a managed identity's replayable token, not the root-cause shape. A plain fully-unauthorized read (no redaction contradiction, no dedicated-permission intent) is classic broken access control, not this insecure-by-design shape. |
| **Multi-cloud note** | The shape is cloud-neutral (read-authz ≠ secret-field-authz). A read op serializes a secret-bearing field to a principal whose read authority excludes knowing that secret — via an unmask/verbosity parameter or plaintext-on-read — while a default view (or the write-gate) redacts it, which is the platform's own proof the value is protected. Negatives everywhere: a secret-store **reference** that still needs the dedicated get permission, or an unmask gated by a separate decrypt permission. |

### SHAPE-032: Caller-Redirectable Credential-Delivery Endpoint (Egress-Target Retarget → Managed Deputy Leaks Its Attached Secret)

> A hybrid origin between `SHAPE-019`, `SHAPE-020`, and `SHAPE-021`, but cleanly none of them. A managed deputy (a credential broker, webhook sender, notifier, relay) authenticates to a **configured delivery endpoint** by attaching a **stored secret** it holds. A caller-writable config field names that endpoint. A principal authorized only to *edit the endpoint* — and deliberately walled from the secret (redacted on read + a denied dedicated retrieve) — retargets the endpoint to an attacker-controlled URL; on the deputy's next dereference it transmits the secret there. The secret is exfiltrated by **redirecting where the deputy delivers it**, defeating the read/retrieve wall. Unlike `SHAPE-019` the borrowed authority is the deputy's **credential**, not its network reach (no SSRF). Unlike `SHAPE-020` a managed **deputy** dereferences the changed field and carries the secret out. Unlike `SHAPE-021` the read path is closed (redacted/denied) — disclosure is via a write + deputy egress.

| Field | Detail |
|-------|--------|
| **Core question** | Does a control-plane update method accept a caller-supplied value for a field that names the endpoint a managed deputy delivers a stored secret to (an OAuth token/authorization URL, a webhook/callback URL with a signing secret, a notification/relay target), applying the change under only a coarse edit permission — so a principal the platform walls from that secret (redacted on read and denied the dedicated retrieve) can redirect where the deputy sends it and thereby obtain the secret it cannot read? |
| **Trust boundary** | A caller with an editor-equivalent role on a resource whose credential is deliberately out of that role's scope → the update method → a caller-writable delivery-endpoint field → the managed deputy that dereferences the field and attaches the resource's stored secret → the attacker-controlled endpoint the field now names. The gate applied is the coarse edit permission; the missing gate is the secret-retrieval authority the credential is otherwise protected by. |
| **Missing control** | Bind the authority to change the delivery endpoint to the authority to receive the credential: before accepting a change to any field that determines where the deputy sends a stored secret, require the caller to hold the secret-retrieval permission on the resource. Equivalent controls: invalidate the stored secret when the endpoint changes (re-supply required), or constrain the endpoint to a validated/registered allowlist. Gate a user-facing authorization URL the same way. |
| **Discovery signal links** | Primary: `SIGNAL-031` (a config-edit role retargets a managed deputy's credential-delivery endpoint despite a read/retrieve wall on that secret — the platform's own contradiction is the signal). Secondary routes: a caller-configurable callback that attaches a beyond-authority credential, and a referent dereferenced by a non-caller deputy. |
| **Safe-control / negative signal** | Safe when the update re-checks secret-retrieval authority on the endpoint change (parity); or the endpoint is validated/allowlisted; or the stored secret is invalidated on endpoint change; or the edit role is itself entitled to the secret (intended config, not escalation); or the deputy attaches no secret; or the endpoint field is immutable after create. Decisive screen: does the platform itself wall the edit role off the secret (redacted read + denied retrieve)? If not, redirecting the endpoint is intended editor power. Where the endpoint is pinned to the credential's own provider domain, treat as blocked only after confirming the provider does not surface the delivered credential to a self-registered tenant on that domain. Keep two authorities distinct when the deputy reads the secret via a caller-supplied platform-delegated identity: the delegation control governs what the deputy may do in the account and is orthogonal to **where** the credential is delivered — a provider that enforces delegation on the credential-write path but not on a destination-only change has the authorization machinery one code path away. |
| **Canon anchors** | None. Distinguished from its `SHAPE-019`/`020`/`021` neighbors above. |
| **Feature-abuse anchors** | An update that re-validates secret-retrieval authority before the endpoint change; a validated/registered redirect-URI-style endpoint; a config where the edit role **is** the secret owner; a deputy that sends no secret; an immutable-after-create endpoint field. |
| **Severity sizing** | By what the leaked secret unlocks × boundary. An OAuth client secret / webhook signing secret / relay credential → impersonation of the connected client or signed-request forgery; intra-service, cross-role, same-project → credential disclosure. A user-delegated token → cross-end-user. An endpoint field that can cross a tenant/owner boundary → higher. The finding is the *authority gap* (a walled secret reaching a caller-chosen endpoint), not that the write or the delivery merely succeeded. |
| **Security Constitution lesson** | The authority to change **where** a managed deputy delivers a credential must be bound to the authority to **receive** that credential. When a platform walls a config-edit role off a secret but lets that role rewrite the endpoint the deputy sends it to, the endpoint field is an unintended egress channel — disclosure by redirection, not intended editor power. The fix is to make a destination change re-enter (and thus re-authorize) the credential configuration, not to bolt a delegation check onto the omit path. Screen for WAI by the platform's own wall (redacted read + denied retrieve) before graduating. |
| **Decoys** | "The endpoint is editable so editing it is allowed" is the mechanism, not the finding — the delta is the walled secret reaching a caller-chosen endpoint. "The deputy made a request" is not enough: the secret must actually reach the caller-chosen endpoint and match the configured secret, and the editor must have had no read/retrieve path to the original. |
| **Confused-with** | `SHAPE-019` if the borrowed authority is network reach (SSRF). `SHAPE-020` if a coarse write reaches a separately-gated mutation with no deputy delivery. `SHAPE-021` if the secret is disclosed on the read path. `SHAPE-026` if the flaw is a target trusting an unbound source principal. `SHAPE-001`/`013` if the deputy acts on a caller-named IAM-bound resource with its own authority (here it exfiltrates its **own** stored secret to a caller-chosen endpoint). |
